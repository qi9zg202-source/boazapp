# Boaz Health

Boaz Health is a local-first iPhone app for the agreed Apple Health and Fitness records. It keeps a protected SQLite copy on the phone. The dark dashboard shows recent sleep, fitness, vitals, timestamps, sample counts, and an audit of what has actually reached Tokyo. Pairing and cloud upload are separate actions; upload starts only after the user grants an explicit second consent.

The Tokyo component is a small Rust receiver with a **separate** SQLite ledger. It never writes into the database replaced by the existing Mac sync. Only the server projects measured values to a verified native VictoriaMetrics process, under `boaz_health_v1_*` metric names. Boaz's existing text-derived metrics remain separate. No Docker, search engine, vector store, graph store, language model, or paid model call is required for this deterministic collection path.

## Scope

The HealthKit allowlist is defined in [`HealthTypeCatalog.swift`](boazapp/Health/HealthTypeCatalog.swift). It covers sleep stages, absolute sleeping wrist temperature, heart and respiratory readings, oxygen saturation, HRV, blood pressure, weight, body fat, BMI, steps, flights, active energy, exercise time, workouts, activity summaries, and available workout events and associated heart-rate samples. The app asks only for read access. HealthKit may return no records when a type is empty or its read access is limited; the app does not infer authorization from an empty result.

Anchored sample imports use bounded pages. Each page and its new anchor are committed together. Activity summaries are fetched in 30-day windows; edits to a day update its stable local identity. Workout edits or deletions invalidate associated detail records and trigger a fresh detail scan. Sleep stages are merged within each session; naps stay separate, and efficiency appears only when in-bed time exists.

## Build the iPhone app

1. Open [`boazapp.xcodeproj`](boazapp.xcodeproj) in Xcode 27 or later. The minimum iOS target is 17. The project uses Swift 6 and Apple frameworks only.
2. Select an Apple development team and a bundle identifier with HealthKit and HealthKit background-delivery entitlements. Confirm that the Health read disclosure shown by iOS names the allowed records.
3. Build and install on a real iPhone paired with the user's Apple Watch. The simulator and CoreDevice service on the development Mac used for this change are currently broken; generic iOS compilation succeeds, but device interaction remains an acceptance gate.
4. In the app, review Health access and import locally. Pair with the private Tokyo `.ts.net` HTTPS address and one-time code. Review the separate upload disclosure, then enable cloud upload. Stop upload or request erasure from Health settings.

Regenerate the project after adding Swift source files with `python3 scripts/generate_xcode_project.py`. The icon is generated by `swift scripts/generate_icon.swift boazapp/Resources/Assets.xcassets/AppIcon.appiconset/AppIcon.png`.

## Tokyo receiver

[`Server/README.md`](Server/README.md) documents the HTTP contract, one-time pairing, native VictoriaMetrics checks, encrypted volumes and backups, Tailscale Serve, recovery, and cloud erasure. The receiver binds to loopback. Its pairing and batch routes stay closed until the operator has verified all deployment gates. The phone keeps unsent records in a durable queue when the private link or service is unavailable.

The visible sync labels have distinct meanings:

- **Local saved:** the iPhone SQLite transaction completed.
- **Cloud saved:** the Tokyo SQLite receipt was returned or recovered by batch ID.
- **Metrics current:** Tokyo confirmed its projection jobs and readback.
- **Erasure pending:** upload is off; the request may still need delivery or Tokyo cleanup may still be running.
- **Erasure complete:** Tokyo confirmed active-record and managed-backup expiry.

## Verification and release gate

Local checks:

```sh
xcodebuild -project boazapp.xcodeproj -scheme boazapp -destination 'generic/platform=iOS' -derivedDataPath /private/tmp/boazapp-dd CODE_SIGNING_ALLOWED=NO build-for-testing
cd Server && cargo test --offline --locked && cargo clippy --offline --locked --all-targets -- -D warnings
```

The iOS test target covers sleep interval conflicts, two nights and a nap, local page/anchor atomicity, bounded upload batches, retries, and tombstones. A native macOS harness also exercised the production ledger against 450 synthetic records. The server tests cover pairing, duplicate and conflicting batches, large history, revisions and deletion, outage behavior, backup integrity, and safety gates.

**AI-NATIVE GATE: INTERCEPT** for enabling real health upload or claiming release readiness. A real iPhone/Watch run, signed installation, HealthKit consent and locked-phone behavior, private Tailscale HTTPS and access rule, Tokyo native VictoriaMetrics identity, encrypted mounts, server socket behavior, end-to-end receipt and metric readback, backup restore, erasure/retention, and rollback drill still require environment-specific evidence. No real health data was uploaded by this repository change.
