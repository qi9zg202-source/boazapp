# Boaz private Health receiver

This service stores iPhone HealthKit records in a separate SQLite ledger and projects selected numeric values to a **native** VictoriaMetrics process. It is not the older Mac-to-Tokyo file replacement target. Nothing here deploys or enables upload automatically.

## Contract

The receiver always binds `127.0.0.1` (default port `8787`). Use Tailscale Serve for private HTTPS; never publish it with Funnel. All routes use JSON. Device routes require `Authorization: Bearer <device-token>`.

1. On the Tokyo host, `boaz-health-receiver pair-code` prints a 10-minute one-use pairing code. Enter it in the app. `POST /v1/health/pairings` with `{"code":"...","device_id":"stable-random-id"}` returns `{"device_id":"...","token":"..."}`. The token is shown only once; store it in the iPhone Keychain.
2. `POST /v1/health/batches` accepts at most 200 events and 128 KiB. Required body: `schema_version:1`, `batch_id`, `device_id`, and `events`. An event has stable `event_id`, monotone `revision`, `operation` (`upsert` or `delete`), `kind` (`quantity`, `category`, `workout`, `activity`), `type`, optional `source` (`bundle_id`, `name`), optional UTC `start_utc`/`end_utc`, optional numeric `value`/`unit`, and object `metadata`. Upserts require source and times; quantity and activity upserts require value and unit. Deletes can omit the latter fields. Activity day identity and timezone belong in its stable event ID and metadata.
3. Successful receipt includes `batch_id`, `status`, `accepted_events`, `changed_events`, `content_hash`, `commit_sequence`, `received_at`, and nullable `projected_at`. `content_hash` is SHA-256 of the exact HTTP request body. `accepted_events` is the parsed batch size, including stale revisions; `changed_events` counts ledger changes. `cloud_saved` proves only the SQLite commit. `metrics_current` requires completion of every relevant projection job; it is immediate if that batch has no metric-eligible events. Repeated identical batch IDs return the original receipt; changed request bytes with the same ID are HTTP 409. `GET /v1/health/batches/{batch_id}/receipt` retrieves a known receipt; `GET /v1/health/status` reports the sample count, pending jobs, and latest commit sequence.
4. A paired device can `POST /v1/health/revoke` to stop credential use without deleting history. An operator can run `boaz-health-receiver revoke-device DEVICE_ID` if the phone is lost.
5. For cloud erasure, the app first saves a random `erasure_id` and 64-hex `erasure_secret` locally. It then calls `POST /v1/health/erase` with the device bearer token and `{"confirmation":"ERASE_CLOUD_HEALTH_DATA","erasure_id":"...","erasure_secret":"..."}`. The transaction removes that device's SQLite events, receipts, pending jobs, token row, and per-device audit rows, leaving a minimal erasure progress record. A lost-response retry sends the same body with the erasure secret as bearer. `GET /v1/health/erasures/{erasure_id}` uses the erasure secret as bearer. States are `pending_metrics`, `pending_backup_expiry`, and `complete`; the response includes separate metrics and managed-backup timestamps plus a 30-day deadline. Keep the erasure secret until `complete`.

The app sends merged deep-sleep minutes as a versioned `boaz.sleep.deep_minutes` quantity event (unit `min`, `source.bundle_id=boazapp`, `metadata.derivation_version=1`). Raw sleep category records are preserved without independently claiming a deep-sleep metric. Supported metric names all start with `boaz_health_v1_`. Unknown or mismatched units remain in SQLite and do not silently become numeric metrics.

## Deployment gate

Compile with `cargo build --release --locked` on the Tokyo Linux host or a verified native Linux toolchain. No Docker is needed. Create a dedicated `boaz-health` user and an encrypted data volume at `/opt/boaz-health/data`; keep this path outside `/opt/boaz/data/boaz_events.db`, which the older Mac sync replaces. Use a separate encrypted backup volume. Restrict directories to that service account. The process sets umask 0077; its SQLite file is mode 0600 and WAL snapshots must stay on the encrypted mount.

Copy [`deploy/boaz-health.env.example`](deploy/boaz-health.env.example) and [`deploy/boaz-health.service.example`](deploy/boaz-health.service.example) to operator-managed paths. Leave all gate flags at `0` until the encrypted mounts, an actual backup restore, and a tailnet-only HTTPS route have been checked. Run VictoriaMetrics as a native binary with `-storageDataPath=<configured absolute path>` and `-httpListenAddr=127.0.0.1:8428`. At startup and again for each ingest request, the receiver verifies the executable path, storage argument, listening argument, ownership of the loopback TCP listener through `/proc`, and required encrypted mounts; a Docker proxy or a mere HTTP 2xx response cannot satisfy it. If any gate fails, the process remains usable for inspection but returns `upload_disabled` for pairing and batches.

After a private tailnet access rule limits phone access to the Tokyo HTTPS service, configure Serve with `tailscale serve --bg http://127.0.0.1:8787` and check `tailscale serve status` from Tokyo and the allowed phone. Do not use Funnel. Use the resulting `https://<Tokyo-tailnet-name>.ts.net` origin in the app. A valid token remains required inside the tailnet. The systemd example is only a template; it is not installed by this repository.

The projection worker never takes a VictoriaMetrics URL from a phone request. It rebuilds each affected metric series from committed SQLite records, allowing changed samples and HealthKit deletions to remove stale points. It verifies an export readback before advancing a receipt or erasure status. If native process identity or HTTP projection fails, the outbox remains pending and receipts remain `cloud_saved`. VictoriaMetrics is a derived store, not the health record authority.

## Backup and recovery

`BOAZ_HEALTH_BACKUP_VOLUME_ENCRYPTED=1 boaz-health-receiver backup /encrypted/backups/boaz-health-YYYYMMDDTHHMMSSZ.db` creates a WAL-aware SQLite snapshot, runs `PRAGMA integrity_check`, and publishes it atomically with a snapshot-start manifest. Backup, erasure, and pruning share an operation lock so a late-published pre-erasure snapshot cannot escape retention. Set the flag only after checking the mounted volume. Schedule `deploy/managed-backups.sh backup` daily and `deploy/managed-backups.sh prune` at least every six hours. The prune command removes managed snapshots at 29 days, before the 30-day erasure deadline, and records when no pre-erasure managed backup remains. Alert on a nonzero exit. Keep all receiver backups in this one managed directory; copies elsewhere are outside this proof and must be tracked separately.

For a restore drill, stop the receiver, preserve the current database, restore one encrypted snapshot to a separate test path, run `PRAGMA integrity_check`, compare receipt and event counts, and start a test receiver against that path with upload disabled. Rebuild projections only after validating the restored ledger and native metrics identity. Never replace the production database without a reviewed rollback plan.

## Local verification

Run `cargo test --offline` and `cargo clippy --offline --all-targets -- -D warnings`. Tests cover one-use pairing, unauthorized access, lost responses, duplicate and conflicting batches, revision tombstones, app units, derived sleep, revocation, and erasure. Real Tokyo HTTPS, native VictoriaMetrics, encrypted mounts, backup restore, and phone end-to-end behavior still require environment-specific verification before enabling upload.
