# Boaz Health test specification

This document defines acceptance requirements and reproducible procedures. It does **not** record a pass merely because a case exists, its test target compiles, or a related unit test passes. Record execution against the exact source revision in the dated acceptance report. The initial design requires all cloud release gates to remain closed until device and Tokyo evidence exists.

## Two-project architecture maintenance — 2026-09-24

The [Boaz project boundaries](https://github.com/qi9zg202-source/TomeofSouls/blob/main/docs/BOAZ_PROJECT_BOUNDARIES.md) preserves the full repository, native Swift responsibilities and current wire/storage contracts. Its [scoped acceptance](https://github.com/qi9zg202-source/TomeofSouls/blob/main/docs/BOAZ_PROJECT_BOUNDARIES_ACCEPTANCE.md) is a separate engineering check; it does not change the historical 77-case register or device/Tokyo dispositions. Required checks are locked offline Server compilation/tests, documentation governance, non-writing Xcode-project verification, and source/artifact/path/link preservation. No HealthKit read, upload, signing or deployment occurs.

## Scope, priorities, and finishing criteria

The subject is the local iPhone application, its private Tokyo receiver, and their recovery path. SQLite is the authoritative record at both ends; VictoriaMetrics is a derived projection. Tests use synthetic health data and isolated storage. Tests that change Tokyo, tailnet policy, device Health data, signing, or production processes require the corresponding authorized environment; do not run destructive steps against existing Boaz records.

| Priority | Meaning | Release rule |
|---|---|---|
| P0 | Consent, privacy, record integrity, authentication, irreversible deletion, or release gate | Every applicable case must pass with current evidence before real upload. Any failure or blocked prerequisite keeps upload disabled. |
| P1 | Required collection, recovery, display, compatibility, or operational behavior | Every applicable case must pass before claiming the first release accepted. |
| P2 | Usability or additional resilience | Record the outcome and resolve material issues; an exception requires an explicit owner and rationale. |

Finishing criteria: compile the app and test target; run all available automated tests; investigate and fix failures within scope; execute the physical iPhone/Watch and isolated Tokyo cases when their prerequisites exist; record precise gaps; and provide repeatable setup, run, restore, and rollback instructions. A build result is not a device test result. An in-process HTTP test is not a private HTTPS test. A mock metrics response is not native VictoriaMetrics persistence evidence. No case can be marked not applicable solely because its environment is unavailable.

Use one of `PASS`, `FAIL`, `BLOCKED`, or `NOT_RUN` in the execution report. `PASS` requires all expected observations for that case. A partial result must describe the verified subset and leave the remaining case `BLOCKED` or `NOT_RUN`. For every run capture case ID, UTC time, tester, source commit and dirty diff hash, command or steps, environment, fixture seed, expected and actual results, evidence path, and defect ID when relevant. Do not store bearer tokens, pairing codes, erasure secrets, or personal health values in committed evidence.
